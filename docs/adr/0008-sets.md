# 0008. Implement sets on the existing hash table, and log random and derived writes as their effect

- Status: Accepted
- Date: 2026-11-15

## Context

Sets hold unique strings without order. Their commands need fast membership tests (`SADD`, `SISMEMBER`, `SREM`), iteration (`SMEMBERS`, `SSCAN` and the set operations), and random choice (`SPOP`, `SRANDMEMBER`).

Two parts of the command set need particular care:

- `SPOP` and `SRANDMEMBER` choose members at random. Replaying a random command from the append-only file would remove different members than the original did.
- `SINTERSTORE`, `SUNIONSTORE` and `SDIFFSTORE` derive their result from other keys. Replaying them is only correct if every source key is in the same state at replay time, including keys that have since expired.

Redis stores small sets of integers as a sorted integer array (`intset`), and from Redis 7.2 small sets of strings as a compact list (`listpack`). Redis 7.0, the version the tests run against, stores sets of strings in a hash table.

## Decision

- **Representation:** a set is a `Dict<SetMember>`, the same incrementally resized, SipHash-keyed table used for the keyspace and hashes (see [0003](0003-incremental-rehashing.md)), with an empty value type. Set members get incremental resizing, protection against hash flooding, and `SSCAN` with the reverse-binary cursor without new code.
- **Random choice** uses the table's `random_entry` with the database's random generator. For `SRANDMEMBER` with a positive count, distinct members are found by shuffling a copy of the member list when more than a third of the set is wanted, and by sampling with rejection otherwise.
- **`SPOP` is logged as its effect:** `SREM key <removed members>`, or `DEL key` when it removes the whole set.
- **The STORE commands are logged as their effect:** `DEL destination`, followed by `SADD destination <members>` in batches of 64. Replay never reads the source keys.
- **Set operations** check the type of every key before computing anything, as Redis does, so a `WRONGTYPE` error leaves the destination untouched. The intersection iterates the smallest set and probes the others, smallest first, and `SINTERCARD` stops at its `LIMIT`.
- **Bounded `SRANDMEMBER`:** with a negative count, members may repeat, so the reply size is not bounded by the data. Redis 7.0.15 accepts counts down to -(2^63 - 1); `SRANDMEMBER key -4611686018427387904` made it unresponsive in testing. kvstore refuses negative counts below -2^20 with an out-of-range error.

## Consequences

- No new data structure: sets reuse a component that is already unit tested against a reference map through growth, shrinking and `SCAN` across resizes.
- Replay of the append-only file is deterministic for every set command, at the cost of larger log entries for `SPOP` with a count and for the STORE commands with large results.
- Memory per member is close to Redis 7.0's, which also uses a hash table for string sets: about 73 bytes per member in a large set against 66 for Redis, and about 283 bytes for a set with one member including its key, against 225. Redis 7.2 and later store small sets more compactly; kvstore does not have compact encodings for any type.
- The `SRANDMEMBER` limit is a deliberate difference from Redis, covered by a `kvstore_only` test.
- `SSCAN` on a small set may take several calls, where Redis returns small compactly encoded sets in one call. Clients must loop until the cursor is 0 in both cases.
